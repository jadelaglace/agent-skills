# 审查判据

按任务选择适用检查。对结论区分已证实、待核与不适用；未检查的条目不写通过。

## 入口与职责

- 按实际宿主检查名称、frontmatter 和发现路径，不把某个平台的限制包装成通用标准。description 清楚说明能力和使用时机；短而可区分优于堆关键词或品牌背书。
- 同时考虑正例、邻近反例和模糊边界。触发词应帮助路由，不以泛化的“凡涉及某领域都调用”挤占其他技能。
- 创建、审查、实施、安装和发布各自的动作边界是否符合用户意图；技能不能自行取得外部写入、删除、消息发送或代理委派权限。
- 不因缺少统一开场白、固定数量的澄清问题或“是否开始”就判严重缺陷。已有上下文足够时应允许开工。

## 指令与结构

- 能否解释每条规则在什么情况下改善结果；把未知条件、用户偏好、宿主限制和不可违背的操作不变量分清。
- 自由度与风险是否匹配：开放任务给目标和判据，脆弱步骤给准确参数与停止条件。不要把所有任务都固定成同一套阶段、目录或审批流程。
- 是否重复基础常识、使用绝对措辞掩盖缺少依据、要求凭空找出若干缺陷，或把“没有看到”变成“不存在”。
- 长资料用相关章节或关键词定位；短而必要的全文可以直接读。不使用自定的字数或行数作为质量裁决。
- 路由、确定性操作、协作写作、环境观察和复杂工程可以组合使用；这些是组织方式，不是必须归类的等级。只有分支真的需要时才拆文件。
- 审美与表达要求要能指导真实输出；不强制所有任务写宣言，不靠替换一组形容词证明质量。

## 工具与依赖

- 引用路径能否解析、资源是否随包提供、依赖是否在当前环境可用；未来规划和未公开内部技能不能算已具备能力。
- 第三方脚本先确认来源、相关实现与副作用；了解调用方式后再运行。只看 --help 不是安全保证。是否读源码、是否修改由任务与风险决定。
- 错误是否保留可诊断信息，有无无界重试、伪造成功、兜底覆盖数据；高风险或外部写操作是否有适用的授权与停止边界。
- 是否尊重现有工作、当前版本和本地约定；修改是否处理根因而不扩大到无关技能。不要以整包替换丢掉本地独立增量。
- 检查实际调用代码及配置中的网络请求、遥测、付费服务或账号依赖，分别说明必要能力和可移除的商业引导；不能只凭作者背景断言存在隐蔽行为。

## 验收与发现

严重程度由影响决定：

| 等级 | 判据 |
| --- | --- |
| 阻断 | 已能说明的越权、数据损坏、核心路径无法执行或误报成功 |
| 重要 | 可复现的结果错误、职责冲突、显著无效工作或关键证据缺口 |
| 改进 | 不阻断结果的清晰度、维护性或上下文成本问题 |

发现使用足够的信息即可：`位置 → 触发条件 → 已见或可推导后果 → 建议`。区分真实执行结果与静态风险推断；带行号时以当前读取的文件为准。

局部修复检查受影响路径；多文件变化同时检查入口、引用和直接依赖。脚本确有变动时跑相关有效检查，不让格式校验代替功能验证。

版权与来源说明有独立用途，不因“去商业化”删除署名或许可。用户请求公开分发时再检查分发范围，不能从“自用”推定要 push、打标签或创建 Release。
